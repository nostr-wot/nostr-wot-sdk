# @nostr-wot/bunker

## 0.2.0

### Minor Changes

- [`302f897`](https://github.com/nostr-wot/nostr-wot-sdk/commit/302f897e5e1bc854ef5ad8a07433b15c513ea996) Thanks [@leonacostaok](https://github.com/leonacostaok)! - New package: `@nostr-wot/bunker`, the NIP-46 responder. `@nostr-wot/signers` and the browser extension are NIP-46 clients; this is the other half, the bunker / remote-signer side of Nostr Connect that they talk to.

  It is a transport adapter and deliberately nothing more. `BunkerServer` listens on relays for kind 24133 requests addressed to a connection key, decrypts the NIP-44 payload, hands the request to one injected `handler`, and publishes the encrypted response. Vaults, permissions, accounts and approval UI never enter the package: every policy decision belongs to the handler, which is why it can sit under a phone app, a desktop signer or a hosted bunker unchanged. Pairing both ways (`createBunkerUri`, `acceptNostrConnect`, `parseNostrConnectUri`), `connect` secret binding, `ping`, `switch_relays`, `logout`, per-client deduplication by request id and event id, clock-skew rejection and an injected logger that never sees a key, a plaintext or a ciphertext are the transport's own business.

  Two keys are never conflated. The connection key signs and encrypts every NIP-46 message and is what a `bunker://` URI advertises. The user key never enters this package at all: `get_public_key` reaches the handler like any other method. That is how Amber and hosted bunkers work, and conflating the two is a mistake the extension's compatibility audit had already found once.

  Only a `BunkerError`'s message is forwarded to a client. Any other throw, a vault exception or a JSON parse error with internal detail in it, becomes `error: "request rejected"`, and a handler that has not settled within `handlerTimeoutMs` is answered with `request timed out`.

  **Persisted state is authenticated.** A phone kills the process constantly, so pairings cannot live only in memory. `exportState()` and `onStateChange` hand out a `BunkerState` (version 2) whose `mac` is an HMAC-SHA256 under a key derived from the connection secret key, and `restore` verifies it before reading anything else: a state that was edited, hand-assembled or signed without that key is refused with `state authentication failed`. That is the case that matters on a phone, where the state sits in ordinary storage and the key sits in the keychain, so the weaker domain cannot forge a pairing. `version` is read before the MAC requirement is decided, so stripping `mac` does not turn a version 2 state into a pre-2 one, and the legacy migration path (`allowUnsigned`) has to be asserted by the host rather than reached by omission. Revocation survives a storage rollback: every `revokeSecret` bumps a monotonic `generation` that lives inside the MAC and beside the key in the host's keychain, and a state behind the host's generation is refused, so restoring an export taken before a revoke cannot bring the revoked client back. Restore is validated whole and applied atomically, with nothing emitted unless it succeeded, so a host persisting on every callback never sees a partial state. `signBunkerState` and `verifyBunkerState` are exported for migration tooling.

  Relay selection is treated as a privacy control, not a delivery detail: a client's responses go only to the relays it was paired on, a relay one client introduced is never used for another's traffic, and it is dropped when that client leaves. Subscriptions are opened on the relay connection itself (`ensureRelay`) rather than through nostr-tools' `pool.subscribe`, because the pool records an event id as seen before it verifies the event, which lets a forged id suppress a genuine request. The reasoning sits in a block comment at the call site and must not be tidied away. Ceilings are hard (`maxSecrets`, `maxClients` counting admissions in flight, `maxRelaysPerClient`), and NIP-04 transport, `create_account`, NIP-89 discovery and relay AUTH are deliberately out of scope.

  Packaging: ESM only, as every package in this release is, and its `dist/` carries the stamp that `npm run check:dist` verifies (inputs and outputs, so a tampered or partially copied `dist/` is refused), which is what makes vendoring it by tarball safe. The stamp machinery the package introduced now lives at the repository root and is shared by every package that has a `check:dist`.
